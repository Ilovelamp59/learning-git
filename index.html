Git Concepts

Eleven core ideas from the cheat sheet—what each one does, when to be careful, how it looks in motion, and where to dig deeper.

Start with repository →

01

Repository (repo)

The project folder tracked by Git—your full history of commits, branches, and tags. Remotes like GitHub host a shared copy so teammates can collaborate.

Considerations

  • Initialize once at the project root, not inside nested random folders.
  • Never commit secrets—use .gitignore for env files and credentials.
  • A bare remote repo is for hosting; your local clone is where you work.

Resources

  • Pro Git — Getting a Repository
  • GitHub Docs — About repositories

02

Clone

Download a full copy of a remote repository onto your machine—including history—so you can work offline and sync later with push and pull.

Considerations

  • Cloning creates a local origin remote pointing at the source URL.
  • Large repos may need shallow clones (--depth 1) for speed.
  • Prefer SSH or HTTPS with a credential helper; don’t paste tokens into shared shells.

Resources

  • git-clone documentation
  • GitHub — Cloning a repository
remote → your machine

03

Branch

A safe parallel timeline of the codebase. You isolate work—features, fixes, experiments—without disturbing main until you’re ready to integrate.

Considerations

  • Keep branches short-lived so they don’t drift far from main.
  • Name them clearly: feat/…, fix/…, chore/….
  • Delete merged remote branches to reduce clutter.

Resources

  • Pro Git — Branches in a Nutshell
  • Atlassian — Using branches
parallel timeline

04

Commit

A snapshot of staged changes plus a message that explains why. Commits are the building blocks of history—small, intentional, and reviewable.

Considerations

  • Stage only what belongs together; avoid “misc fixes” mega-commits.
  • Write messages that answer “why,” not just “what files changed.”
  • Don’t rewrite commits already pushed to a shared branch without team agreement.

Resources

  • git-commit documentation
  • Conventional Commits

05

Push / Pull

Push uploads your local commits to the hosted repo. Pull downloads remote updates into your working copy so you stay in sync with the team.

Considerations

  • Pull (or fetch + merge/rebase) before pushing to reduce conflicts.
  • git pull --rebase keeps a cleaner linear history when appropriate.
  • Force-pushing to shared branches is dangerous—avoid on main.

Resources

  • git-push documentation
  • git-pull documentation
  • GitHub — Getting remote changes
upload ↔ download

06

Diff

The visual difference between two versions of code—often across commits or branches. Diffs power code review by showing exactly what changed.

Considerations

  • Review your own git diff before committing or opening a PR.
  • Whitespace and formatting noise can hide real changes—normalize when possible.
  • Binary files don’t diff well; prefer text formats for reviewable assets when you can.

Resources

  • git-diff documentation
  • GitHub — Comparing branches

07

Merge

Combine one branch back into another—usually integrating a feature branch into main. Git creates a merge commit when histories diverged.

Considerations

  • Merge commits preserve exact branch history; useful for auditing how work landed.
  • Resolve conflicts carefully and test after merging.
  • Teams often prefer squash merges on GitHub for a tidy main.

Resources

  • Pro Git — Basic Branching and Merging
  • GitHub — About pull request merges
branches converge

08

Rebase

Replay your commits on top of the latest main. Instead of a merge commit, you get a linear history as if you started from the newest base.

Considerations

  • Never rebase commits that others already based work on—rewrites history.
  • Great for cleaning up a local feature branch before a PR.
  • Conflicts can appear commit-by-commit; resolve carefully with --continue.

Resources

  • Pro Git — Rebasing
  • Atlassian — git rebase

09

Merge conflict

Two changes touched the same lines and Git can’t auto-combine them. You choose the correct final version, mark the file resolved, then continue.

Considerations

  • Read both sides; the “right” fix might be a third combination of both.
  • Remove conflict markers (<<<, ===, >>>) before committing.
  • Communicate with the author of the other change when intent is unclear.

Resources

  • Pro Git — Checking out conflicts
  • GitHub — About merge conflicts

10

Pull Request (PR)

A request to review and merge your branch—“please take a look, then merge this into the target branch.” The hub for discussion, checks, and approval.

Considerations

  • Keep PRs focused; small diffs get better reviews.
  • Describe intent, test plan, and any screenshots or risk notes.
  • Wait for required checks and reviews before merging.

Resources

  • GitHub — About pull requests
  • How to write the perfect pull request
please review & merge

11

Issue

A ticket tracking a bug, feature, or task. Issues capture context, discussion, and acceptance criteria before (and while) code ships.

Considerations

  • Write a clear title, steps to reproduce (for bugs), and desired outcome.
  • Label by type and priority so the backlog stays scannable.
  • Link PRs to issues so closing work updates the board automatically.

Resources

  • GitHub — About issues
